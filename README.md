# rewind

**Undo and redo for Shiny applications.**

Shiny has bookmarking, which captures a state you can link to. It has
`reactlog`, which lets *you* replay a session while debugging. It has no
undo — the thing every user already expects from every other application they
use.

`rewind` adds it in one line.

```r
library(shiny)
library(rewind)

ui <- fluidPage(
  rewind_buttons(),
  selectInput("region", "Region", c("North", "South", "East", "West")),
  sliderInput("year", "Year", 2018, 2026, 2024),
  plotOutput("plot")
)

server <- function(input, output, session) {
  rewind_enable()          # <- that's it

  output$plot <- renderPlot(plot_for(input$region, input$year))
}

shinyApp(ui, server)
```

`Ctrl+Z` now walks backwards through the user's filter choices. `Ctrl+Shift+Z`
walks forwards.

## What it does

### Coalescing, so undo means something

Dragging a slider fires dozens of input events. Undoing them one at a time
would be useless. Changes that land within `coalesce_ms` (default 400) of each
other become a single history entry, so one drag is one undo step.

### Explicit steps, when time isn't the right boundary

A "reset filters" button changes four inputs at once and deserves one entry
with a name a human wrote:

```r
observeEvent(input$reset, {
  rewind_step(label = "Reset filters", {
    updateSelectInput(session, "region", selected = "All")
    updateSliderInput(session, "year", value = c(2018, 2026))
    updateCheckboxInput(session, "active_only", value = FALSE)
  })
})
```

### Server-side state, not just inputs

Anything you keep in `reactiveValues` is invisible until you say otherwise:

```r
state <- reactiveValues(pinned = character(0), zoom = 1)
rewind_track(state, fields = c("pinned", "zoom"))
```

### A history rail

`rewind_ui()` renders the stack as a scrubbable list. Click any step to jump
straight to it. Labels are generated from what actually changed, so it reads
`region, year` rather than `state 7`.

```r
ui <- fluidPage(
  sidebarLayout(
    sidebarPanel(rewind_ui()),
    mainPanel(...)
  )
)
```

## How restore works

The part worth knowing about, if you plan to extend this.

Restoring a value means putting it back in the widget, and the naive approach
is a lookup table: `sliderInput` → `updateSliderInput`, `selectInput` →
`updateSelectInput`, and so on for every input type in existence. That table is
never finished, and it breaks the moment someone uses a widget from a package
you have not heard of.

So `rewind` doesn't have one. Every Shiny input registers an **input binding**
against its DOM element, and every binding exposes `setValue()` or
`receiveMessage()`. The client-side code looks the binding up and calls it:

```js
var binding = $el.data("shiny-input-binding");
if (typeof binding.setValue === "function") {
  binding.setValue(el, value);
} else {
  binding.receiveMessage(el, { value: value });
}
```

That is the whole restore path, and it works for third-party inputs for free.

### The echo problem

Restoring an input sends it to the browser, which sets it, which reports the
new value back to the server — where the capture observer sees a change and
records a new history entry. That is a loop, and it is the failure mode this
kind of package usually dies of.

Two things prevent it, deliberately overlapping:

1. **Dedup.** The history refuses to push a state identical to the current one.
   Since a restore sets the pointer to state S *before* the echo arrives, the
   echo is by definition identical to the present and is dropped. This handles
   the common case with no coordination at all.
2. **An expectation guard.** The controller remembers what it asked the browser
   to apply, and ignores intermediate states until either the echo matches or
   two seconds pass. This covers the case where inputs arrive in separate
   flushes and produce a half-applied state that dedup would not catch.

Neither depends on a timing assumption about the round trip, which is what
makes this robust rather than merely usually-correct.

## What is deliberately not captured

- **Action buttons and links.** Their value is a click counter; restoring one
  either does nothing or spuriously re-fires whatever observes it.
- **`fileInput()`.** Its value points at a server-side temp file that Shiny
  deletes on the next upload, so restoring an old snapshot would point at a
  path that no longer exists.
- **Inputs beginning with `.`**, which are Shiny's own.
- **Inputs beginning with `rewind_`**, which are this package's.

## Known limitations

Being honest about the edges, since they will bite you before the docs do:

- **Values round-trip through JSON.** Dates come back as strings, integers as
  doubles. Comparison is tolerant of this, but an input holding an exotic
  R object will not survive. Keep exotic state in `reactiveValues` and track it
  there, where no serialisation happens.
- **Modules.** Calling `rewind_enable()` inside a `moduleServer()` works and is
  tested: inputs are captured under their module-local names (the same names
  `input$` sees inside that module) and re-qualified with `session$ns()` on
  restore. `session$userData` is shared across modules, so calling it in more
  than one module reuses the same session-wide history rather than creating
  independent ones per module - call it once, wherever in the module tree
  suits your app.
- **Undo does not undo side effects.** If an observer wrote to a database when
  the filter changed, stepping back changes the filter, not the database.
- **`renderUI`-generated inputs** are captured once they exist, but undoing to
  a state before they existed will leave them at their current values.

## API

| Function | Purpose |
|---|---|
| `rewind_enable()` | Turn on capture for the session |
| `rewind_track()` | Add `reactiveValues` fields to the history |
| `rewind_step()` | Group changes into one labelled entry |
| `rewind_undo()`, `rewind_redo()`, `rewind_jump()` | Drive the history yourself |
| `rewind_clear()` | Drop everything but the present |
| `rewind_pause()`, `rewind_resume()` | Suspend capture around programmatic churn |
| `rewind_disable()` | Fully tear down capture for the session |
| `rewind_history()`, `rewind_can_undo()`, `rewind_can_redo()` | Inspect, reactively |
| `rewind_buttons()`, `rewind_ui()` | Drop-in UI |
